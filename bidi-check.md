# Bidi Check — PDF vs HTML Arabic Text Comparison

## Objective
PDF text extraction is a common source of bidirectional (bidi) text failures for Arabic — 
characters or glyphs can come out reversed or reordered even when the PDF renders correctly 
on screen. This document records how that check was performed for this corpus, what was 
found, and how detected failures are handled.

---

## Method

For every Arabic PDF in the corpus, its extracted text is compared against the extracted 
text of its **matching HTML twin** (same page, same language, different format — 
`corpus/ar/mobile-lines.pdf` vs `corpus/ar/mobile-lines.html`).

The comparison uses `difflib.SequenceMatcher` to compute a similarity ratio between 0 and 1:
- **1.0** = identical text
- **Closer to 0** = the two extractions diverge heavily, which for a PDF/HTML pair of the 
  *same underlying content* strongly indicates the PDF's text layer is corrupted rather than 
  the pages simply having different content.

A threshold of **0.5** is used: below it, the PDF is rejected rather than ingested, since 
attempting to auto-correct character-level reordering is unreliable and risks silently 
introducing wrong text into the corpus (worse than rejecting outright).

This check runs automatically inside `extract_pdf()` (see `_check_bidi_against_html`) for 
every PDF that has a same-named `.html` file in the same folder.

---

## Finding: `corpus/ar/mobile-lines.pdf` — reversal confirmed

**Similarity ratio: 0.24** (well below the 0.5 threshold) → file rejected.

### Evidence — extracted text side by side

| Expected (from HTML, correct) | Actual (from PDF, corrupted) |
| :--- | :--- |
| شخصي | شخيص |
| الأعمال | األعمال |
| إنترنت | إنرتنت |
| فايبر | فايرب |
| الارتداء | اإلرتداء |

The corruption is at the **character level within words** (letters swapped/reordered inside 
a word, plus stray extra alef characters), not a whole-line or whole-paragraph reversal. This 
was confirmed by extracting at word-level granularity (`page.get_text("words")`) — individual 
words were *already* garbled before any line-joining logic ran, ruling out a text-extraction 
ordering bug on our side.

### Root cause
The corruption exists in the PDF's embedded text layer itself, not in how it's read. The 
Arabic PDF was generated by `weasyprint` from the same HTML as its English counterpart. The 
**English PDF from the same generator has no such issue** (confirmed by inspection — English 
text extracts cleanly), which isolates the defect to Arabic glyph shaping/encoding during 
PDF generation, not to PyMuPDF's extraction logic.

We also tried PyMuPDF's alternative extraction modes (`sort=True`, word-level extraction, 
raw text flags) — all produced the same corrupted output, confirming the defect is baked 
into the PDF file, not fixable by choosing a different extraction method.

### Decision: reject, don't repair
Because the corruption is character-level and inconsistent (not a simple global reversal), 
any attempt to "fix" it programmatically (e.g. reversing character order) would be a guess, 
not a reliable transformation. Reporting a wrong answer read aloud by a contact-center agent 
is a worse failure than clearly refusing to ingest a broken document. The pipeline therefore 
rejects this file with a clear, logged reason, and the matching HTML/DOCX versions of the 
same page (which extract cleanly) remain available in the corpus as the source of truth for 
that content.

| | Arabic PDF | English PDF |

| Generator | weasyprint | weasyprint |

This side-by-side confirms the defect is Arabic-specific, not a general flaw in the PDF 
generation or extraction pipeline.

---

## Scope of this check
This bidi check only runs for PDFs that have a matching HTML file in the same folder (used 
as the ground-truth reference). PDFs without an HTML twin are not checked this way and pass 
through if their text layer is otherwise non-empty — a limitation worth revisiting if 
PDF-only sources are added later without a paired HTML/DOCX version.
